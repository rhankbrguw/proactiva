# Engineering Standards

## Code Authorship

All code must read as written by a senior engineer, not generated by an AI.

- No filler comments. Comments explain _why_, never _what_ — the code itself must be self-documenting.
- No `// Initialize the variable` or `// Call the function` style noise.
- Comment only on non-obvious decisions: algorithm choices, workarounds, business constraints.
- No placeholder text, no TODO left in final output, no `// ...rest of implementation`.
- Function and variable names eliminate the need for comments wherever possible.

---

## Architecture

Every project follows strict layered architecture. No exceptions.

```
Request → Controller / Handler / Route
               ↓
           Service / Use Case       ← all business logic lives here
               ↓
           Repository               ← all data access lives here
               ↓
           Database / External API
```

- Controllers: parse input → call service → return response. Zero logic.
- Services: business rules only. No HTTP, no DB queries, no framework code.
- Repositories: data access only. No business logic.
- UI Components: render only. No business logic, no direct API calls.

Dependency direction: outer layers depend on inner layers. Inner layers never import outer layers.

---

## File & Function Constraints

- Maximum **150 lines** per file. Exceed this → split by responsibility.
- Maximum **30 lines** per function. Exceed this → extract.
- Maximum **3 levels** of nesting. Exceed this → use guard clauses and early returns.
- One responsibility per file. One purpose per function.
- Zero unused imports. Zero unused variables. Zero dead code.

---

## Naming

- Functions: verb + noun → `getUserById`, `processPayment`, `validateOrderItems`.
- Booleans: `is`, `has`, `can`, `should` prefix → `isActive`, `hasPermission`, `canRetry`.
- No abbreviations except universally known ones: `id`, `url`, `api`, `http`, `ctx`, `err`.
- No: `data`, `info`, `temp`, `obj`, `val`, `x`, `foo`, `result2`, `myFunction`.
- Constants: `SCREAMING_SNAKE_CASE`. Enums: `PascalCase` members.

---

## Zero Hardcode Policy

Every value that could change per environment or context must be externalized.

- Colors, spacing, typography → design tokens / theme constants. Never inline (`text-white`, `#fff`, `Colors.white`).
- Strings: route names, labels, error messages, success messages → string constants file.
- Numbers: timeouts, limits, retries, pagination sizes → named constants.
- URLs, hostnames, ports, credentials → environment variables via validated config layer.
- Feature flags, toggles → config, never source code booleans.

---

## Unified Constants System

Every project must have a centralized constants layer:

```
constants/
├── colors.(ts|dart|go)       ← all color tokens
├── strings.(ts|dart|go)      ← all user-facing strings and messages
├── routes.(ts|dart|go)       ← all route names/paths
└── config.(ts|dart|go)       ← all env-driven config values
```

No string literal, color value, or magic number may appear outside these files. If a new string or color is needed, add it to the constants file first, then reference it.

---

## Validation

- Validate at the boundary (controller/handler/route) before anything reaches a service.
- Validate every field that enters the system — type, format, range, required.
- Use schema-based validation (Zod, class-validator, go-playground/validator, Dart's validation).
- Return all validation errors at once — never one field at a time.
- Services must receive already-validated, typed data. Services never call raw validation.

---

## Error Handling

- Never swallow errors silently. No empty `catch {}`, no `_ =` on errors, no `!` in Dart without proof.
- Errors are typed. Create domain-specific error/exception types — never throw raw strings.
- Expected failures (not found, unauthorized, conflict) → return typed error from service, handle at controller.
- Unexpected failures (infra, network, DB) → catch at global handler, log with full context, return 500.
- Every `catch` block either recovers with intent or re-throws with added context.
- Go: always wrap errors → `fmt.Errorf("userService.Create: %w", err)`.

### Exception Hierarchy

```
AppException (base)
├── ValidationException    → 422
├── AuthException          → 401
├── ForbiddenException     → 403
├── NotFoundException      → 404
├── ConflictException      → 409
└── InternalException      → 500
```

## API Response Contract

Every API response follows this envelope. No deviation.

**Success:**

```json
{
  "success": true,
  "code": "OK",
  "message": "User retrieved successfully.",
  "data": {},
  "meta": { "timestamp": "...", "request_id": "..." }
}
```

**Error:**

```json
{
  "success": false,
  "code": "USER_NOT_FOUND",
  "message": "The requested user could not be found.",
  "errors": null,
  "meta": { "timestamp": "...", "request_id": "..." }
}
```

**Validation failure:**

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "The given data was invalid.",
  "errors": {
    "email": ["Required.", "Must be a valid email address."],
    "password": ["Minimum 8 characters."]
  }
}
```

Message rules:

- Human-readable, actionable, non-technical.
- No stack traces, no SQL messages, no internal paths in production.
- Error codes: `SCREAMING_SNAKE_CASE`, domain-prefixed → `ORDER_NOT_FOUND`, `USER_EMAIL_CONFLICT`.

## UI/UX Standards (Frontend & Flutter)

### Design Philosophy

- Every UI decision must have intent. No decoration for decoration's sake.
- Avoid "AI default" aesthetics: no generic purple gradients, no Inter/Roboto unless intentional, no rounded cards on white backgrounds as the default answer.
- Reference real product design: Linear, Vercel, Stripe, Arc, Raycast, Craft. Study what makes them feel premium.
- Distinctive > generic. If it looks like every other app, it's wrong.

### Design Tokens (non-negotiable)

- Every color, spacing, radius, shadow, duration → token. Zero hardcoded values anywhere.
- Token naming: semantic over literal → `color.surface.primary` not `gray.100`, `color.text.danger` not `red`.
- All tokens defined in one place: `constants/tokens.(ts|dart|css)`. Single source of truth.
- Dark mode support is not optional — design token system must support theme switching from day one.

### Typography

- Font pairing: one display font + one body font maximum. Never three or more.
- Never use: Inter, Roboto, Arial, Space Grotesk as a default — these signal AI-generated UI.
- Type scale: defined as tokens (xs, sm, md, lg, xl, 2xl, 3xl). No arbitrary `font-size: 13px` inline.
- Line height, letter spacing → tokens. Never inline.
- Hierarchy must be obvious at a glance: one clear visual focal point per screen.

### Spacing & Layout

- 8pt grid system. All spacing values multiples of 4 or 8.
- No arbitrary pixel values. Use spacing tokens: `space.4`, `space.8`, `space.16`, etc.
- Consistent padding within component categories — cards always use the same internal padding.
- Max content width defined as a token. Never let text stretch full viewport on wide screens.

### Color

- Color palette: 1 primary, 1 accent (optional), neutral scale, semantic colors (success, warning, danger, info).
- Contrast ratio: minimum 4.5:1 for body text (WCAG AA). 3:1 for large text and UI components.
- Never use pure black (`#000`) or pure white (`#fff`) — use near-black and off-white for softer rendering.
- Glassmorphism, gradients, shadows: use intentionally, never as filler decoration.

### Component States

Every interactive element must implement all states — no exceptions:

- Default, hover, active/pressed, focused, disabled, loading, error, success, empty.
- Focus states must be visible and styled (not browser default outline).
- Disabled state must look clearly different — not just `opacity: 0.5`.

### Motion & Animation

- All durations and easing curves → constants. Never inline.
- Entry: ≤ 300ms. Exit: ≤ 200ms. Micro-interactions: ≤ 150ms.
- Easing: `ease-out` for entrances, `ease-in` for exits, `ease-in-out` for transitions.
- No animation that plays on every render — only on state change or user interaction.
- Reduced motion: respect `prefers-reduced-motion`. Wrap all animations in a check.
- Stagger animations for lists: 30–50ms delay between items, not all at once.

### Feedback & States

- Skeleton loaders for content areas, never blank screens. Spinners only for triggered actions.
- Toast/snackbar for non-blocking feedback. Modal only when action requires explicit confirmation.
- Empty states must be designed — not a blank div. Include illustration or icon, message, and action.
- Error states must offer recovery: retry button, go back link, or corrective action.
- Success states must be visible but brief — auto-dismiss after 3 seconds.

### Accessibility

- Semantic HTML/widget tree always. No `div` where a `button` belongs.
- All images, icons, illustrations → meaningful alt text or `aria-hidden="true"` if decorative.
- Keyboard navigation must work on every interactive element without a mouse.
- Touch targets: minimum 48×48dp (Material) / 44×44pt (iOS/HIG). Never smaller.
- Screen reader tested before shipping any new component.

### Mobile-First (Flutter & React Native & responsive web)

- Design for the smallest target screen first, scale up.
- Safe area insets respected on all screens — never content behind notch or home indicator.
- Scroll behavior: overscroll handled, pull-to-refresh where appropriate, infinite scroll with skeleton.
- Bottom navigation for primary actions on mobile — not top nav.
- Gesture conflicts resolved: swipe-to-dismiss must not conflict with scroll.

---

## Performance

- No premature optimization — but no obvious inefficiencies either.
- Avoid N+1 queries: always eager-load relationships.
- Index every foreign key and every column used in WHERE/ORDER clauses.
- Paginate all list endpoints — never return unbounded arrays.
- Memoize expensive computations that are called repeatedly with the same input.
- UI: virtualize long lists. Never render all items into the DOM/widget tree.
- Avoid unnecessary re-renders: memoize components, use selectors for state slices.

## Stack-Specific Rules

### Go

- `context.Context` is the first parameter of every function that does I/O.
- Interfaces for all external dependencies — enables testing without real infra.
- No global state. Dependencies via struct fields or constructors.
- No business logic in `main.go` or HTTP handlers.
- Folder: `internal/domain/`, `internal/service/`, `internal/repository/`, `internal/handler/`.

### TypeScript / Node.js

- `strict: true` in tsconfig. No `any` without an inline justification comment.
- Runtime validation via Zod schemas — schemas live in `src/schemas/`.
- `async/await` always. No raw `.then()` chains.
- DI container or explicit constructor injection — no service locator pattern.
- Folder: `src/controllers/`, `src/services/`, `src/repositories/`, `src/schemas/`.

### React / Next.js

- `.tsx` only. Zero `.jsx` files.
- Server state: TanStack Query. UI state: Zustand or Jotai. No mixing.
- Forms: `react-hook-form` + Zod resolver. No `useState` for form fields.
- Server Components for data fetching. Client Components only where interactivity is required.
- Folder: `components/` (UI), `hooks/` (logic), `services/` (API), `constants/`.

### Laravel / PHP

- PHP 8.3+. Type-hint all parameters, return types, and class properties.
- Form Requests for all validation. API Resources for all responses.
- Service + Repository pattern. No raw queries in controllers or models.
- Enums for all fixed value sets (PHP 8.1+ backed enums).
- Folder: `app/Services/`, `app/Repositories/`, `app/Http/Resources/`, `app/Enums/`.

### Flutter / Dart

- Null safety enforced. No `!` without proof and an explanatory comment.
- Architecture: pick one per project — BLoC or Riverpod. Never mix.
- `freezed` for all data models. `go_router` for navigation.
- `dio` with interceptors for HTTP. Repositories abstract all network calls.
- Folder: `lib/features/[feature]/data/`, `domain/`, `presentation/`.

### Svelte / SvelteKit

- TypeScript always. `lang="ts"` on every `<script>` block.
- No inline styles, no hardcoded color values — use CSS custom properties defined in a global theme file.
- Component state: Svelte stores (`writable`, `readable`, `derived`) for shared state. Local `$state` rune (Svelte 5) for component-only state.
- Server-side data fetching in `+page.server.ts` / `+layout.server.ts` — never `fetch` in component `onMount` for initial data.
- Form handling: SvelteKit form actions (`+page.server.ts` `actions`) + `superforms` + Zod schema. No manual fetch for form submissions.
- API calls go through `src/lib/services/` — never called directly from components.
- Folder: `src/lib/components/` (UI), `src/lib/stores/` (state), `src/lib/services/` (API), `src/lib/constants/`, `src/routes/` (pages + server).
- Error handling: `+error.svelte` at every route segment that needs a custom error UI. `error()` helper from `@sveltejs/kit` for expected failures.
- No `any` types. Run `svelte-check` clean before considering code done.

## Pre-Code Checklist

Before writing any code, confirm:

1. Which layer? Controller / Service / Repository / UI / Constants
2. DRY check — does this logic already exist?
3. Where do new strings, colors, and config values go?
4. What are the failure cases and how is each handled?
5. What does the success and error response look like?
6. Will this file stay under 150 lines?
